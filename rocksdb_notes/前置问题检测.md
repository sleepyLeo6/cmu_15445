# 第一阶段：首先真正理解 LSM-Tree

## 问题回答

### 1. 为什么 B+ Tree 的随机更新可能带来较高的 I/O 成本？

B+ Tree 通常按 key 定位并修改叶子页。随机更新的 key 可能分散在不同页中：

- 读取：目标页不在缓存时，需要从磁盘读入；分散访问会产生随机读 I/O。
- 写回：修改后的页成为脏页，最终需要写回磁盘。即使只修改少量数据，也通常按页写回，可能产生写放大。
- 插入导致页分裂时，还可能额外修改其他页和父节点。

### 2. 为什么 LSM-Tree 选择先写入内存？

LSM-Tree 先把更新写入内存中的 MemTable，是为了把分散的小更新积累起来，再批量写入磁盘，降低随机写 I/O 成本。

流程是：

1. 追加写 WAL：记录更新，支持崩溃恢复。
2. 更新 MemTable：在内存中维护数据，避免每次更新都去修改磁盘中的数据页。
3. 批量刷盘：MemTable 达到阈值后，将有序数据写成 SSTable，使这部分磁盘写入主要采用顺序写。

### 3. MemTable 为什么通常需要保持 Key 有序？

主要是为了高效地生成有序 SSTable，同时支持范围查询。

1. 刷盘时可以直接按 Key 顺序输出

SSTable 中的数据通常按 Key 排序。如果 MemTable 已经有序，刷盘时遍历它就能顺序生成 SSTable，无需临时对全部数据排序。

例如，更新按下面的顺序到达：

```
Put(8, "A")
Put(2, "B")
Put(5, "C")
```

MemTable 按 Key 组织后，遍历顺序为：

```
2 → "B"
5 → "C"
8 → "A"
```

这个顺序可以直接用于生成 SSTable。

2. 支持高效的范围查询

例如查询 2 ≤ Key ≤ 6，有序结构可以先定位到 Key 2，再依次遍历，直到 Key 超过 6。如果只有无序哈希表，范围查询通常需要扫描整张表

# 其他问题

## 为什么顺序写入对于 SSD 也能减少开销

SSD 虽然没有磁头寻道，但仍有写入粒度、垃圾回收和处理 I/O 请求的开销。 LSM-Tree 的大块顺序写通常能减少这些开销。

1. SSD 不能直接覆盖已有的闪存数据<br>
NAND 闪存按 page 写入、按更大的 block 擦除。更新某个逻辑地址时，SSD 通常会：<br>
- 把新数据写到空闲位置；
- 将旧位置标记为无效；
- 之后通过垃圾回收，搬走某个 block 内仍然有效的数据，再擦除整个 block。<br>
随机更新容易让有效数据和无效数据混在多个 block 中，回收时就需要搬运更多有效数据，产生额外写入，也就是 SSD 内部的写放大。顺序写通常更有利于数据组织和回收，减少这些搬运。Micron 技术说明

2. LSM-Tree 还把小写入合并成了大写入<br>
例如，假设需要写入 1 MiB 数据：

| 写入方式 | 请求数量 |
|---|---:|
| 每次写 4 KiB | 256 次 |
| 合并为一次 1 MiB 写入 | 1 次 |

每次请求都需要提交、排队和完成处理。批量写可以摊薄这些开销，也更容易充分利用设备带宽。这里的收益来自批量化，顺序地址让合并请求更容易。

因此，对 LSM-Tree 更准确的理解是：

> 它将分散的小更新缓冲起来，转化成大块顺序写，既减少请求开销，也通常更适合 SSD 内部的闪存管理。

不过收益取决于 SSD 控制器和负载；而且 LSM-Tree 后续的 Compaction 会再次读写数据，所以顺序写并不意味着整个系统的总写入量一定更少。

## LSM-Tree 先写内存，要是断电了怎么办？

这是理解 LSM-Tree 时非常重要的一点。

MemTable 是内存数据结构，本身不具备持久性。

因此，RocksDB 等持久化 LSM-Tree 存储引擎通常采用 WAL（Write-Ahead Log）。

典型写入路径：
```
              PUT(key, value)
                    |
           +--------+--------+
           |                 |
           v                 v
       WAL (磁盘)      MemTable (内存)
           |                 |
     持久化日志           更新有序结构
                             |
                         Flush
                             |
                             v
                      SSTable (磁盘)
```

注意图中 WAL 与 MemTable 是同一写入路径的两个组成部分，并非表示它们一定并行执行或独立提交。

WAL 也需要磁盘写入，但它与 B+ Tree 的数据页原地修改不同：
- WAL 主要采用 Append（追加写入）。
- MemTable 承担有序数据组织。
- Flush 负责批量生成 SSTable。
如果发生崩溃，数据库可以利用已持久化的 WAL 恢复尚未 Flush 的数据。

因此，LSM-Tree 并不是完全避免磁盘写入，而是将磁盘写入分成日志追加和批量生成 SSTable 两种形式。

还需要区分：写入 WAL 文件与 WAL 真正持久化并不是一回事。是否在返回写入成功前执行 fsync 或等价持久化操作，取决于具体配置和持久性要求。

### WAL 和 MemTable 在 LSM-Tree 中是怎样被使用的？

典型顺序是：先追加 WAL，再更新 MemTable，最后返回写入成功。 WAL 用来恢复尚未写成 SSTable 的内存数据。RocksDB 官方文档

所以前面说的“先写内存”，更准确地说是：先在内存中积累数据，再批量生成 SSTable；这个过程仍然需要先记录 WAL。

以 Put("a", 10) 为例：
```
收到 Put("a", 10)
        ↓
向 WAL 末尾追加这次操作
        ↓
如果要求同步持久化，等待 WAL 同步到持久存储
        ↓
在 MemTable 中插入 a → 10
        ↓
向调用者返回成功
```

这里要区分 “追加 WAL”与“WAL 已经持久化”：

| 写入模式 | 返回成功前的保证 |
|---|---|
| 同步写，例如 RocksDB 的 `sync=true` | 等待 WAL 同步到持久存储 |
| 非同步写 | WAL 可能仍在操作系统缓存中，机器崩溃或断电可能丢失最近写入 |

因此，启用了 WAL，不等于每次返回成功时都已经落盘。RocksDB 写入选项说明

WAL 的作用可以通过两个崩溃时刻理解：

- WAL 已持久化，MemTable 还没更新就崩溃：重启后重放 WAL，将 a → 10 重新插入 MemTable。这次操作可能还没来得及向调用者返回成功。
- MemTable 已更新，但尚未生成 SSTable 就崩溃：MemTable 随进程消失，但同样可以通过持久化的 WAL 恢复。

等 MemTable 被安全地刷成 SSTable，且数据库记录了这些文件后，对应数据就不再依赖 WAL 恢复。当某个 WAL 中所有需要恢复的数据都已安全刷盘时，这个 WAL 才可以被回收。RocksDB WAL 生命周期

你可以记成：WAL 按操作到达顺序记录更新，负责恢复；MemTable 按 key 组织数据，负责查询和后续有序刷盘
