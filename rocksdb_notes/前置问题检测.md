# 第一阶段：首先真正理解 LSM-Tree

## 问题回答

### 1. 为什么 B+ Tree 的随机更新可能带来较高的 I/O 成本？

B+ Tree 通常按 key 定位并修改叶子页。随机更新的 key 可能分散在不同页中：

- 读取：目标页不在缓存时，需要从磁盘读入；分散访问会产生随机读 I/O。
- 写回：修改后的页成为脏页，最终需要写回磁盘。即使只修改少量数据，也通常按页写回，可能产生写放大。
- 插入导致页分裂时，还可能额外修改其他页和父节点。

### 2. 为什么 LSM-Tree 选择先写入内存？

LSM-Tree 先把更新写入内存中的 MemTable，是为了把分散的小更新积累起来，再批量写入磁盘，降低随机写 I/O 成本。

流程是：

1. 追加写 WAL：记录更新，支持崩溃恢复。
2. 更新 MemTable：在内存中维护数据，避免每次更新都去修改磁盘中的数据页。
3. 批量刷盘：MemTable 达到阈值后，将有序数据写成 SSTable，使这部分磁盘写入主要采用顺序写。

### 3. MemTable 为什么通常需要保持 Key 有序？

主要是为了高效地生成有序 SSTable，同时支持范围查询。

1. 刷盘时可以直接按 Key 顺序输出

SSTable 中的数据通常按 Key 排序。如果 MemTable 已经有序，刷盘时遍历它就能顺序生成 SSTable，无需临时对全部数据排序。

例如，更新按下面的顺序到达：

```
Put(8, "A")
Put(2, "B")
Put(5, "C")
```

MemTable 按 Key 组织后，遍历顺序为：

```
2 → "B"
5 → "C"
8 → "A"
```

这个顺序可以直接用于生成 SSTable。

2. 支持高效的范围查询

例如查询 2 ≤ Key ≤ 6，有序结构可以先定位到 Key 2，再依次遍历，直到 Key 超过 6。如果只有无序哈希表，范围查询通常需要扫描整张表

### 4. WAL 如何支持崩溃恢复？

具体回答可以参考[LSM-Tree 先写内存，要是断电了怎么办](#lsm-tree-先写内存要是断电了怎么办)

### 5. SSTable 为什么可以设计成不可变文件？

因为 LSM-Tree 把更新和删除记录为新版本，不需要直接修改旧 SSTable。

例如，某个 SSTable 已经保存：

a → 10

执行 Put(a, 20) 时，新值先经过 WAL 写入 MemTable，之后刷到新的 SSTable。旧文件中的 a → 10 可以保留，查询时根据版本顺序选择最新值：

旧 SSTable：a → 10
新 MemTable / SSTable：a → 20  ← 查询返回这个版本

删除也一样：写入一个 删除标记（tombstone），让查询知道旧值已经失效。

之后，Compaction 读取已有 SSTable，合并数据并生成新的 SSTable，在满足安全条件时清理旧版本和删除标记，再回收旧文件。

因此可以回答：

> SSTable 可以设计成不可变文件，因为 LSM-Tree 的更新和删除通过写入新版本或删除标记完成，查询时识别最新版本；后续通过 Compaction 生成新文件并清理失效数据，无需原地修改旧 SSTable。

这样也使 SSTable 的数据、索引和过滤器在生成后保持稳定，简化并发读取和缓存管理。

### 6. 为什么必须存在 Compaction？

因为不断刷盘会积累 SSTable、旧版本和删除标记，需要 Compaction 来控制查询成本并回收空间。

假设同一个 Key 经历了三次操作，分别刷入不同文件：

SSTable 1：a → 10
SSTable 2：a → 20
SSTable 3：a → 删除标记

查询 a 时，结果已经是“不存在”，但旧值仍占用磁盘空间。

如果一直不做 Compaction：

- 文件不断增加：一次查询可能需要检查更多 SSTable；范围查询还需要合并更多有序数据流。
- 失效数据不断累积：旧版本和已删除的数据持续占用空间。
- 层级结构难以维持：对于分层 LSM-Tree，需要通过合并将数据向下层迁移，并控制各层大小与 Key 范围重叠。

Compaction 会读取一组 SSTable，合并其中的有序数据，生成新的 SSTable，并在安全时淘汰旧版本、回收旧文件。快照仍需要的版本不能删除；删除标记也必须保留到它不会导致更深层旧值重新出现时，才能清理。

可以回答为：

> Compaction 用于合并 SSTable、清理不再需要的旧版本和删除数据，控制文件数量与层级结构，从而降低查询开销并回收磁盘空间。没有它或类似的整理机制，持续更新会使读取成本和空间占用不断增长。

代价是：合并需要额外读写数据，这也是 LSM-Tree 写放大的重要来源

### 7. 为什么 LSM-Tree 会出现 Read、Write、Space Amplification？

这三种放大，都来自 LSM-Tree 的设计：更新先写成新版本，数据分散在多个 SSTable 中，再通过 Compaction 整理。

| 类型 | 含义 | 产生原因 |
|---|---|---|
| Read Amplification（读放大） | 一次逻辑查询，需要做多次底层读取 | 数据分散在多个文件或层级中，查询可能需要检查多个 SSTable；范围查询还需要合并多个有序数据流 |
| Write Amplification（写放大） | 底层实际写入量大于用户写入量 | 数据先写 WAL，再刷成 SSTable，之后又可能在多次 Compaction 中被重新写入 |
| Space Amplification（空间放大） | 实际占用空间大于有效数据大小 | 旧版本、删除标记尚未清理；Compaction 期间，新旧文件还会暂时共存 |

例如，用户把 a 从 10 更新为 20：

旧 SSTable：a → 10
新 SSTable：a → 20

- 读放大：查询可能需要检查多个文件，才能确定最新版本。
- 写放大：a → 20 写入 WAL、SSTable，之后还可能被 Compaction 重写。
- 空间放大：逻辑上只需要最新值，但磁盘暂时保留了两个版本。

三者之间存在权衡：更积极的 Compaction 通常能减少读放大和空间放大，但会增加合并带来的写入开销。Bloom Filter、索引和缓存则可以减少查询实际产生的磁盘读取。

## 问题回答

### 2. immutable memtable 为什么 flush 不能阻塞全部写入？

lsm tree 中，当 memtable 达到阈值后，会触发 flush 操作，通常是这样的流程：
1. 将它冻结为 Immutable MemTable，交给后台线程 Flush 成 SSTable。
2. 创建一个新的 Mutable MemTable，继续接收写入。

如果 Flush 期间阻塞全部写入，那么每次 MemTable 写满，所有写请求都要等磁盘写完。磁盘比内存慢得多，这会造成吞吐量下降，以及周期性的写延迟尖峰。

Immutable 的作用正是让这两件事安全地并行：后台线程读取已经冻结的数据，前台线程写入新的 MemTable，双方不修改同一份数据。

不过，如果写入速度长期超过 Flush 速度，导致 Immutable MemTable 堆积、内存达到上限，系统仍然需要减速甚至暂停写入，这称为 write stall（写停顿）。

所以，这个设计的目标是：正常情况下用后台 Flush 隐藏磁盘延迟，积压过多时再对写入施加背压

# 其他问题

## 为什么顺序写入对于 SSD 也能减少开销

SSD 虽然没有磁头寻道，但仍有写入粒度、垃圾回收和处理 I/O 请求的开销。 LSM-Tree 的大块顺序写通常能减少这些开销。

1. SSD 不能直接覆盖已有的闪存数据<br>
NAND 闪存按 page 写入、按更大的 block 擦除。更新某个逻辑地址时，SSD 通常会：<br>
- 把新数据写到空闲位置；
- 将旧位置标记为无效；
- 之后通过垃圾回收，搬走某个 block 内仍然有效的数据，再擦除整个 block。<br>
随机更新容易让有效数据和无效数据混在多个 block 中，回收时就需要搬运更多有效数据，产生额外写入，也就是 SSD 内部的写放大。顺序写通常更有利于数据组织和回收，减少这些搬运。Micron 技术说明

2. LSM-Tree 还把小写入合并成了大写入<br>
例如，假设需要写入 1 MiB 数据：

| 写入方式 | 请求数量 |
|---|---:|
| 每次写 4 KiB | 256 次 |
| 合并为一次 1 MiB 写入 | 1 次 |

每次请求都需要提交、排队和完成处理。批量写可以摊薄这些开销，也更容易充分利用设备带宽。这里的收益来自批量化，顺序地址让合并请求更容易。

因此，对 LSM-Tree 更准确的理解是：

> 它将分散的小更新缓冲起来，转化成大块顺序写，既减少请求开销，也通常更适合 SSD 内部的闪存管理。

不过收益取决于 SSD 控制器和负载；而且 LSM-Tree 后续的 Compaction 会再次读写数据，所以顺序写并不意味着整个系统的总写入量一定更少。

## LSM-Tree 先写内存，要是断电了怎么办？

这是理解 LSM-Tree 时非常重要的一点。

MemTable 是内存数据结构，本身不具备持久性。

因此，RocksDB 等持久化 LSM-Tree 存储引擎通常采用 WAL（Write-Ahead Log）。

典型写入路径：
```
              PUT(key, value)
                    |
           +--------+--------+
           |                 |
           v                 v
       WAL (磁盘)      MemTable (内存)
           |                 |
     持久化日志           更新有序结构
                             |
                         Flush
                             |
                             v
                      SSTable (磁盘)
```

注意图中 WAL 与 MemTable 是同一写入路径的两个组成部分，并非表示它们一定并行执行或独立提交。

WAL 也需要磁盘写入，但它与 B+ Tree 的数据页原地修改不同：
- WAL 主要采用 Append（追加写入）。
- MemTable 承担有序数据组织。
- Flush 负责批量生成 SSTable。
如果发生崩溃，数据库可以利用已持久化的 WAL 恢复尚未 Flush 的数据。

因此，LSM-Tree 并不是完全避免磁盘写入，而是将磁盘写入分成日志追加和批量生成 SSTable 两种形式。

还需要区分：写入 WAL 文件与 WAL 真正持久化并不是一回事。是否在返回写入成功前执行 fsync 或等价持久化操作，取决于具体配置和持久性要求。

### WAL 和 MemTable 在 LSM-Tree 中是怎样被使用的？

典型顺序是：先追加 WAL，再更新 MemTable，最后返回写入成功。 WAL 用来恢复尚未写成 SSTable 的内存数据。RocksDB 官方文档

所以前面说的“先写内存”，更准确地说是：先在内存中积累数据，再批量生成 SSTable；这个过程仍然需要先记录 WAL。

以 Put("a", 10) 为例：
```
收到 Put("a", 10)
        ↓
向 WAL 末尾追加这次操作
        ↓
如果要求同步持久化，等待 WAL 同步到持久存储
        ↓
在 MemTable 中插入 a → 10
        ↓
向调用者返回成功
```

这里要区分 “追加 WAL”与“WAL 已经持久化”：

| 写入模式 | 返回成功前的保证 |
|---|---|
| 同步写，例如 RocksDB 的 `sync=true` | 等待 WAL 同步到持久存储 |
| 非同步写 | WAL 可能仍在操作系统缓存中，机器崩溃或断电可能丢失最近写入 |

因此，启用了 WAL，不等于每次返回成功时都已经落盘。RocksDB 写入选项说明

WAL 的作用可以通过两个崩溃时刻理解：

- WAL 已持久化，MemTable 还没更新就崩溃：重启后重放 WAL，将 a → 10 重新插入 MemTable。这次操作可能还没来得及向调用者返回成功。
- MemTable 已更新，但尚未生成 SSTable 就崩溃：MemTable 随进程消失，但同样可以通过持久化的 WAL 恢复。

等 MemTable 被安全地刷成 SSTable，且数据库记录了这些文件后，对应数据就不再依赖 WAL 恢复。当某个 WAL 中所有需要恢复的数据都已安全刷盘时，这个 WAL 才可以被回收。RocksDB WAL 生命周期

你可以记成：WAL 按操作到达顺序记录更新，负责恢复；MemTable 按 key 组织数据，负责查询和后续有序刷盘

### 什么是 sst file 中的 data block

Data Block（数据块）是 SST 文件中存放一批 Key-Value 记录的单元。 一个 SST 文件通常包含多个 Data Block。

以 RocksDB 常见的 BlockBasedTable 格式为例，可以简化成：

一个 SST 文件
```
┌──────────────────────────┐
│ Data Block 0：a → 1, b → 2 │
│ Data Block 1：d → 3, f → 4 │
│ Data Block 2：h → 5, k → 6 │
├──────────────────────────┤
│ Filter：辅助判断 Key 是否存在 │
│ Index：定位 Data Block    │
│ 其他元数据、Footer        │
└──────────────────────────┘
```

这些记录按 Key 有序，相邻记录被组织进同一个 Data Block。

查询 f 时，大致是：

1. 通过 Index Block，定位到可能包含 f 的 Data Block 1。
2. 如果该块不在缓存中，就从文件读取；如果经过压缩，还需要解压。
3. 在块内查找 f，得到值 4。

所以可以这样区分：

| 单位 | 作用 |
|---|---|
| SST 文件 | 保存一组有序记录及其索引等辅助信息 |
| Data Block | 保存其中一段有序记录，是常用的读取、压缩和缓存单元 |
| Key-Value 记录 | 一条具体的数据 |

这里的 Data Block 是 SST 文件格式定义的逻辑块，不一定等于操作系统的页、SSD 的物理页或 NAND 擦除块。
